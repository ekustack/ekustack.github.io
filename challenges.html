Chart design challenges

Master real ProvChart configs: series count, labels, themes, stacking, gauges, and layout. Each challenge gives a goal, a payload, what the output should feel like, and design notes you can reuse on production data.

How to run: Paste payloads into Pro Dashboard or POST /api/v1/generate with your API key. Free signed-up accounts get 5 test gens/month. Replace colors freely — structure matters more.

Design rules before you code

  • One message per chart. If you need two messages, use two charts or a combo with a clear primary.
  • Label the axes of meaning. axisX should be human categories (months, teams), not raw indexes.
  • Series names are the legend. Prefer “Revenue” over “Series 1”.
  • Color encodes identity, not rank (unless it’s a sequential heatmap-style design).
  • ProvChart scale: points are typically on a 0–100 visual scale (or normalize your domain into that range).
  • Containment: fix height, use a card surface, keep legend under or beside — don’t let bars kiss the edge without padding in the theme.

Suggested palette order for multi-series challenges (violet → teal → amber → rose → mint → blue).

Challenge 01

One series, clear story

1 serieslinelabels

Goal: A single trend that a reader understands in under 3 seconds — title-worthy name, month labels, one color.

{
  "type": "line",
  "series": [
    { "name": "Monthly active users", "color": "#8b7bff", "points": [22, 28, 31, 35, 42, 48, 55] }
  ],
  "axisX": ["Jan", "Feb", "Mar", "Apr", "May", "Jun", "Jul"]
}

Design note: If the story is “growth,” keep points monotonic-ish; if “volatility,” deliberately zig-zag — don’t mix messages.

Challenge 10

Theme system

themebrandstructure

Goal: Same data, three skins. Prefer API theme string or custom theme object if your plan supports it.

  "theme": "midnight",
  "series": [

  ],
  "axisX": ["Jan", "Feb", "Mar", "Apr", "May", "Jun"]

Repeat with "theme": "dark" and a light theme if available. Structure stays; only surface, grid, and text tokens change.

Challenge 11

Real data makeup (normalize)

datascaleproduction

Goal: Map real domain values into the chart’s 0–100 visual language.

// Raw revenue in thousands: [120, 145, 132, 180, 210]
// min = 120, max = 210
// normalized = (v - min) / (max - min) * 100
// → [0, 28, 13, 67, 100]

{
  "type": "bar",
  "series": [
    { "name": "Revenue", "color": "#4fd8c4", "points": [0, 28, 13, 67, 100] }
  ],
  "axisX": ["Jan", "Feb", "Mar", "Apr", "May"]
}

Expected:

Alternative: Keep absolute-ish scale if all points already sit in 0–100 (percent metrics).

Challenge 12

Layout containment & labels

layouta11ycards

Goal: Ship a chart that feels “designed,” not pasted.

  • Wrap output in a card: padding 16–20px, radius matching your design system.
  • Put a visible title above the chart (HTML heading), not only a series name.
  • Add a one-line summary for screen readers / SEO: e.g. “MAU rose from 22 to 55, Jan–Jul.”
  • Keep a data table nearby for accessibility (accessible charts guide).
  • For README: use /api/v1/generate-svg and commit a file — not a fragile data URI (Markdown guide).

Expected: Chart + title + optional table in one contained module; works in a dashboard grid without clipping legends.

Scoring yourself

  • Would a teammate name the chart’s message without reading your explanation?
  • Are series names production-ready?
  • Would this still work at 375px width?
  • Did you normalize real data deliberately?
  • Is color count ≤ series count (no unused accents)?
API tip: HTML → POST /api/v1/generate · SVG → POST /api/v1/generate-svg · same body shape for type / series / axisX. See API docs.

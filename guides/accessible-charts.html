Accessible charts

Charts are visual by nature — but they don’t have to exclude keyboard users, screen reader users, or people who need stronger contrast. This guide covers practical a11y patterns, and how pure CSS charts help.

Why chart accessibility is hard

Many libraries draw on canvas or dense SVG with little structure. Assistive tech then sees a blank image or a shallow tree. Users who can’t see color or fine detail lose the data story entirely.

Good accessible charts usually need:

  • A text alternative (summary or data table)
  • Enough contrast and not color-only encoding
  • Clear labels and titles
  • Keyboard access when the chart is interactive
  • Markup that stays in the accessibility tree when possible

How pure CSS charts help

ProvChart outputs HTML + CSS. Shapes live in the DOM (or as styled elements), not in a single opaque bitmap. That makes it easier to:

  • Attach accessible names and descriptions
  • Pair every chart with a real data table
  • Keep first-paint content visible to crawlers and tools alike

Interactivity is still your responsibility — but the base graphic is already “in the page,” not locked inside a JS runtime.

Checklist (use on every chart)

  • Title — visible heading or aria-labelledby
  • Summary — one or two sentences of what the chart shows
  • Data table — same numbers in a semantic <table> (visible or linked)
  • Not color alone — patterns, labels, or shapes as well as color
  • Contrast — text and critical lines meet WCAG where possible
  • Keyboard — if interactive, focusable controls and visible focus
  • Reduced motion — respect prefers-reduced-motion for transitions

1. Always provide a text alternative

A chart without a text alternative fails WCAG’s non-text content idea in practice. Minimum pattern: 

<figure>
  <figcaption id="rev-caption">
    Revenue vs target, Feb–Aug 2026
  </figcaption>
  <div id="chart"
       role="img"
       aria-labelledby="rev-caption"
       aria-describedby="rev-desc">
    <!-- ProvChart HTML injected here -->
  </div>
  <p id="rev-desc" class="visually-hidden">
    Revenue rose from 312 to 483 over seven months, staying above target each month.
  </p>
  <details>
    <summary>View data table</summary>
    <table>...</table>
  </details>
</figure>
Pro tip: Generate the short summary from the same analytics you send to the API (“max point”, “trend up/down”, “top category”). Don’t rely on the image alone.

2. Pair every chart with a data table

Tables are the most reliable accessible representation of the same data. Options:

  • Visible table under the chart
  • <details> / “Show data” disclosure
  • Link to a full accessible report page

Screen reader users and anyone who can’t parse the graphic can still get the numbers.

3. Color is not enough

ProblemFix
Series only differ by hueAdd labels, patterns, or distinct stroke styles
Low contrast on dark UIUse theme tokens with stronger text/grid contrast
Status only as red/greenAdd icons or text (“+12%”, “Below target”)

ProvChart themes let you set text, muted, and series colors explicitly — tune them for contrast, not just aesthetics.

4. Label axes and units

Include axis labels or a caption that states units (“$ thousands”, “% of sessions”). Ambiguous numbers are inaccessible numbers.

5. Keyboard and focus (interactive charts)

Pure CSS charts from the API are static by default — good for many embeds. If you add your own controls (toggles, time range, series switches):

  • Use real <button> / <select>, not clickable divs
  • Keep a visible :focus-visible style
  • Don’t trap focus inside the chart without an exit

6. Motion

Height/clip transitions look nice; they can distract or cause issues for some users. 

@media (prefers-reduced-motion: reduce) {
  .pc-chart * {
    transition: none !important;
    animation: none !important;
  }
}

7. Using the ProvChart API accessibly

  1. Generate chart with POST /api/v1/generate
  2. Inject HTML/CSS into a figure with caption + description
  3. Render a table from the same series data you sent to the API
  4. Set series colors that pass contrast against your surface
const data = await res.json();
if (data.success) {
  chartEl.innerHTML = data.html;
  document.head.insertAdjacentHTML('beforeend', `<style>${data.css}</style>`);
  // Also build <table> from the same `series` / `axisX` you posted
}

Quick do / don’t

  • Do give every chart a name and a short prose summary
  • Do expose the underlying data in a table
  • Do test with a screen reader and keyboard only
  • Don’t rely on color alone to mean “good” or “bad”
  • Don’t ship canvas-only charts with no alternative text
  • Don’t hide the only copy of the data inside a PNG in email without a summary
